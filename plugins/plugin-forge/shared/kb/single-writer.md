# 单写者与幂等纪律

插件平台三端并发写同一个 cap.kv（面板 + 服务 + MCP + 多设备同账号），没有事务、没有 CAS。**所有竞态必须靠键空间契约消灭，而不是靠运气。** 已验证的两套模式：

## 模式一：单写者 + 命令通道（推荐，page-sentinel/clip-relay/data-ark 验证）

每个键空间指定**唯一写者**（通常是服务进程），其他端只能：

- 写「命令键」表达意图：`<prefix>.cmd.<op>.<nonce> = { op, ..., at }`
- 读「结果键」拿产出：`<prefix>.result.<nonce>`

```
面板/MCP                     服务（唯一写者）
   │ 写 cmd.check.<id>          │
   ├──────────────────────────▶│ tick 扫到命令键
   │                            │ ① 先删命令键（先删后做！防重复消费）
   │                            │ ② 执行
   │  轮询读 state/result        │ ③ 写结果/状态键
   │◀──────────────────────────┤
```

**「先删后做」是幂等核心**：先 `kvDel` 成功后才执行。两个消费者同时扫到同一命令键时，kv delete 天然互斥（后删者失败），执行至多一次。

**面板轮询注意**：1200ms 间隔 + 30s deadline + 超时给明确指引（「服务可能未运行，去设置页看」）。绝不建议面板长轮询高频键——每秒全量 `list` 会拖垮全局。

## 模式二：多方写不同键 + id 幂等（pocket-ledger 验证）

没有服务进程时（纯面板+MCP），允许多方写**各自独立**的键；同一实体键（如账单）以内容 id 为主键，双端并发写同 id 产生相同内容（幂等），冲突无害。适用「写操作天然带唯一 id」的场景。

## 大变更：租约 + 原子落盘（data-ark 验证，重活必用）

- **kv 租约**：`{ holder, expiresAt }`，TTL 90s / 30s 续租。持租者才能做重活；租约过期别的进程可抢。解决「两个服务实例同时跑大任务」。
- **结果文件原子写**：先写 `<file>.tmp` 再 `fs.renameSync`（同盘 rename 原子），manifest 类"索引"最后写——崩溃后要么完整要么没有。
- **错过调度只补一次**：服务重启后发现错过周期任务，只补最近一次，不回放历史（防止补风暴）。

## 禁止清单

- ❌ 用 setTimeout/超时"解决"同步问题——超时掩盖竞态，竞态还在
- ❌ 面板和服务同时写同一个键（没有 CAS，后写覆盖先写）
- ❌ 命令键「读完再删」——两个消费者都读到，双执行
- ❌ 假设 kv list 和 get 之间数据没变——读到的键可能已被删，**所有 get 都要 `.catch(() => null)` 并容忍 null**
