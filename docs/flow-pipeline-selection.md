# 选型文档：自动化流水线（flow-pipeline）

> 2026-11-03 · 第 55 号插件选型记录。方向硬约束（2026-11-01 用户定案）：台账/记录/家庭生活类一律不进候选池；主攻工具/技术/自动化执行/内容变换。

## 一、生态饱和度盘点（先内后外）

Polaris-plugin 现 81 条目。与本选型相关的既有覆盖：

| 既有插件 | 覆盖 | 与本选型关系 |
|---|---|---|
| task-runner 定时任务台 | 提醒 / HTTP 探测 / AI 提示词 / 命令行，**单任务**定时执行 | 原子能力之一；无多步、无数据传递、无 MCP 工具调用 |
| webhook-station | 入站回调**接收/检查/重放**（调试视角） | 无下游动作编排 |
| relay-devkit v1.5.1 | API 客户端 / JSON / SQL / DB / 时间戳工具箱 | 排除「API 调试台」「开发者工具箱」两个候选 |
| repo-lens | git 仓库八维体检（只读分析） | 排除「Git 体检台」 |
| diff-desk | 文本/JSON/目录/URL 对比 | 排除「接口对比台」 |
| data-query | CSV/Parquet SQL（DuckDB） | 排除「数据透视台」 |
| mock-server | 假接口服务 | 排除「Mock 台」 |
| page-sentinel / feed-radar / paper-radar / news-curator | 网页变化盯守 / RSS / arXiv / AI 刊物（**固定形态**） | 均为单目标产品，无通用编排层 |
| capability-runtime | AI 工具热插拔模组 | 扩展 AI 能力面，非工作流组合 |

**结论：生态里有很多「原子能力」（单步执行器、触发器、接收器），缺一层「组合层」——把这些原子能力按数据流串成会自动跑的多步流水线。没有任何插件提供。**

## 二、候选池（≥10，全部过方向硬闸）

1. **自动化流水线台（flow-pipeline）** —— 多步数据管道：HTTP→提取→模板→AI→MCP 工具→落盘/通知，四种触发。开发者/重度用户的自动化组合层。✅ 入围
2. 开发者工具箱 —— ❌ relay-devkit v1.5.1 已占（API 客户端+格式化+SQL+DB）。
3. API 调试台（Postman 类）—— ❌ relay-devkit 的 API 客户端 + cURL 导入 + 代理已覆盖主干。
4. Mock 接口台 —— ❌ mock-server 已交付。
5. Git 仓库体检台 —— ❌ repo-lens 已交付。
6. 数据透视台 —— ❌ data-query 已交付。
7. TOTP 2FA 验证码台 —— 外部证据真（Authy 桌面版 2024-03 停服，[The Register](https://www.theregister.com/software/2024/02/15/twilio-reminds-users-that-authy-desktop-apps-die-in-march/558751)、[用户迁移博文](https://jpmens.net/2024/02/17/notes-to-self-authy-desktop-is-dead)），但 Ente Auth / KeePassXC / Bitwarden 已免费补位且体验成熟；插件形态还要承担加密保险库的全部安全责任。❌ 竞争劣势+安全责任过重
8. 音频转写台（whisper ONNX）—— 需求真，但模型 40MB+ 下载、CPU 转写慢，免费竞品（飞书妙记/Buzz/whisper.cpp 桌面）强。❌ 性价比不足
9. 视频变换台（ffmpeg）—— 需求真（HandBrake 存在但 CLI 恐惧真实），但 ~100MB 二进制顶 CDN 50MB 抖动红线，且本质是「ffmpeg GUI」，差异化弱。❌ 交付风险>增量价值
10. 局域网扫描台（nmap-lite）—— net-sentinel 已覆盖网络质量视角；端口扫描对 Polaris 用户场景偏窄。❌
11. i18n 工具台 —— 生态无覆盖但受众窄（Polaris 本身中文单语）。❌
12. 签名调试台（微信支付/企微 webhook 签名）—— 痛点真实但极窄频。❌ 可作为后续独立小插件。

## 三、市场证据（方向 1：工作流自动化）

- r/selfhosted、r/automation 反复出现「n8n 太重、想本地轻量方案」主题帖（自托管摩擦：Docker/Postgres/升级/资源；webhook 静默丢失吐槽）。社区共识替代品 Windmill / Huginn / Activepieces / Node-RED 全是**需要另行安装维护的独立服务端**——没有一个「已经在跑的桌面应用里顺手就有」的形态。
- Zapier/Make 云端方案：数据出域、订阅费、不能触达本机文件与本地服务。
- n8n GitHub 生态规模（自托管工作流引擎事实标准）证明品类需求为真；Polaris 插件形态 = 零额外基础设施（宿主常驻）+ 数据不出本机 + AI 对话式搭建 + **宿主 50+ 插件的 MCP 工具直接当步骤用**（任何独立工作流引擎都没有的组合优势）。

## 四、评分（方向 1；权重×5 分制→100）

| 维度 | 权重 | 得分 | 依据 |
|---|---:|---:|---|
| 用户痛点强度 | 20% | 4 | 「重复的多步操作」是开发者/重度用户每天实际发生的摩擦；n8n 品类规模证明痛感 |
| 频率与覆盖人群 | 15% | 4 | 自动化一旦搭好每周必跑；覆盖开发/数据/运维/内容多人群 |
| 现有方案缺口 | 15% | 4 | 轻量本地方案全是独立服务端；Polaris 生态内零组合层（task-runner 只能单步） |
| 可验证差异化 | 15% | 5 | MCP 工具即步骤 = 全网独有；宿主常驻零部署；AI 对话式搭建 |
| 用户收益与价值 | 15% | 4 | 一次搭建长期自动跑；从「记得去跑」变成「自动发生」 |
| 插件形态适配 | 10% | 5 | 面板+服务+MCP 三件套完全是既有 house 范式；kvclient/cap.mcp 通路全部已验证 |
| 技术可行性 | 5% | 5 | 零依赖 Node 全部可达成；无新二进制、无 CDN 风险 |

## 五、决策与止损

- **选**：flow-pipeline 自动化流水线。核心动作 = 「自动化执行了什么」，完全合规于方向硬闸。
- **最大不确定性**：用户是否愿意用「表单式线性管道」而不是上 n8n。验证方式：MVP 聚焦 9 类步骤 + 四触发 + 运行历史，交付后看真实使用（守望台用量）。
- **止损**：若管道编辑器复杂度失控，先交付「运行器+全部执行器+MCP 工具」并砍拖拽/分支 UI（线性+when 门控已覆盖主场景）；不引入画布编辑器。
- **MVP 明确不做**：画布编辑、并行分支、循环、子管道调用、云同步、team 协作、内置通知渠道（notify 步骤经 webhook 覆盖钉钉/企微/飞书/Bark）。
