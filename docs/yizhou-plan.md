# 译舟 yizhou 选型与产品方案（2026-11-01）

> 双语沉浸阅读插件：把任意网页链接抓取 → 抽正文 → AI 逐段翻译成中外对照 → 存进本地跨端阅读器。
> 对话式入口（「帮我把这篇翻译成双语」），数据面 `yz.*`（cap.kv），**零服务进程**。

## 一、选型过程（先证明值得做）

### 1.1 生态盘点（避免重复造轮子）

`index.json` 全量 56 条逐条过：记账/台账域 15+（pocket-ledger/duzhi/abacus/quanfu/piaoxia/jinkui/changqi/shouzha/guanzhi/wenjin/chexia/maian/qingnang/ask-stove/tether…）、监控哨兵域 8（page-sentinel/quote-sentinel/net-sentinel/feed-radar/paper-radar/pocket-host/disk-radar/time-trail）、AI 创作域 6（flashforge/qimu/gezhi/xintu/agnes/animation-*）、知识管理 6（memoryforge/lingxi/time-sift/weibian/amber/decision-journal）。
**翻译/双语阅读：生态零覆盖**（唯一命中 "translation" 的是 zcode-adapter 的「格式翻译」，无关）。需求库 27 条均为平台/核心向，无用户侧翻译需求积压。

**用户方向约束（2026-10-28 定案记忆）**：用户明确否决「记录/复盘类」的重复堆叠（决策日志、习惯、周报全被否），要求「创造模式，或者更强的」。故本轮候选池全部为**能力型**。

**淘汰理由**：自动化流水线——与核心仓 `cap.scheduler`（需求 003 已 specd）和 capability-runtime 职责相撞；feed-radar/page-sentinel/paper-radar 已覆盖头部定时自动化场景；在 AI 常驻的 Polaris 里静态流水线的边际价值低。照片管家——聊天优先应用里做图片库浏览 UX 天然别扭；媒体文件重、面板 iframe 能力受限。故事工坊——需求依赖「家有幼儿」这一未验证假设（用户家庭构成未知），市场证据比翻译薄一个量级。设备哨兵——低频，且与 net-sentinel 天然相邻，适合做其后续迭代而非独立插件。

### 1.3 市场证据（可追溯）

- **需求规模**：「沉浸式翻译」2023-05 发布 5 个月 40 万用户（被推文科技收购独立运营）；2026-09 官宣用户破 **3000 万**，入选 Chrome 2024 全球最佳扩展。双语对照阅读是已被 3000 万人投票的真实需求。
- **付费痛点**：Pro 会员包年约 500-700 元（约 $8/月），GitHub issue #2429 用户抱怨「一年 500 实在有点贵」「免费版像试用」；用户自购 API Key 月成本 <5 元的对比讨论活跃——**自带模型、零订阅**是已被用户用脚投票的价值点。
- **隐私事件**：2025-08 被曝分享链接功能把翻译结果（含用户保单、合同）存放在可公开访问的存储中——**纯本地存储**是直接回应。
- **形态缺口**：上述产品全是浏览器扩展（绑定单一浏览器、无本地跨端阅读库）；Polaris 面板运行在 Tauri webview（无内置翻译能力），手机 PWA 浏览器的系统翻译无双语对齐、无缓存、无隐私控制。复制粘贴给 AI 聊天翻译则丢失排版、无法沉淀复用。
- **本用户画像佐证**：paper-radar 订阅 LLM/Agent 主题、日常读英文技术文档——高频真实使用者。

| 假设 | 验证方式 | 不成立时 |

## 二、产品定义

- **一句话**：把「读外文网页要开翻译、贴给 AI、读完就丢」变成「一句话入舟，中外交对照，本地跨端随时读」。
- **目标用户**：每天读英文技术文档/论文/资讯的开发者与知识工作者；家中有外语资料需求的家庭成员。
- **MVP 范围**：URL 抓取+抽取+AI 对话式逐段翻译（批量契约+断点续译）+ 双语阅读面板（双语/译文/原文三态、字号、进度记忆、复制导出）+ 跨端同读（cap.kv）。**暂不做**：EPUB/PDF/字幕翻译、面板一键免对话翻译（需服务进程，二期）、整页排版还原（只保结构化正文）、术语表/记忆库。
- **成功指标**：一篇 6k 字符文章从「对 AI 说翻译」到面板可读 ≤ 2 分钟、≤ 4 次工具往返；断点续译可恢复；面板三端打开同一进度。

## 三、架构（零服务，三件套复用）

```
AI 对话 ──MCP 6 工具（yz_fetch/more/save/list/read/delete）──┐
  yz_fetch：MCP 进程原生 fetch（无跨域）→ 琥珀同款打分抽取    │
  → markdown-lite 分段 → cap.kv yz.* 入库 → 返回批次+翻译契约  │
  yz_save：逐批 upsert 译文（幂等，断点续译）                  ▼
                                        cap.kv yz.* 键空间
面板（库/阅读器）──__POLARIS_HOST_INVOKE__→router_dispatch──┘（只读 art、只写 pos）
```

复用清单：`service/html.js`（DOM 解析）、`service/extract.js`（打分抽取，新增 extractBlocks 导出）、`service/charset.js`（BOM/头/meta 三级字符集）、`service/kvclient.js`（端点自发现桥，env 供测试注入）；MCP 骨架与打包按 maian/flashforge 范式。

### 键空间契约（权威，三方一致）

| 键 | 写者 | 内容 |
|---|---|---|
| `yz.idx` | **仅 MCP** | 文章索引数组 [{id,url,site,title,srcLang,tgtLang,segCount,totalChars,translated,batches,addedAt}] |
| `yz.art.<id>.p.<c>` | **仅 MCP** | 段落分块（100 段/块）[{i,src,dst?,at?}]，c=块号 |
| `yz.pos.<id>` | **仅面板** | 阅读进度 {segIdx,pct,at} |
| `yz.settings` | 仅面板 | {mode,fontScale} |

安全边界：抓取只在 MCP 进程（无 CORS 面）；面板零外网；译文即用户自己的模型产出，不出设备；抓取大小/时长上限（3MB/20s）+ 总量上限（12 万字符）防失控。

## 四、验收（MVP）

1. 单测：批次规划/幂等合并/进度计算/索引维护/抽取分段（含 GBK、JS 空壳、导航噪声 fixture）全绿。
2. 内存桥全链路：stub 宿主 HTTP + 真实 stdio server，六工具全流程（fetch→save×N→list→read→delete）断言通过。
3. 真实宿主冒烟（Polaris 运行中）：kv 真读写 + 键集自清理，不留测试数据。
4. `tsc --noEmit` + esbuild 面板构建通过；打包 `node scripts/pack.js plugins/yizhou` 成功。
5. 已知边界如实进 README（SPA 动态页抓不到、代码段不译、重抓清译文、翻译消耗用户模型 token）。
